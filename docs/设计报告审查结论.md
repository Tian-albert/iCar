# iCar 软件设计报告（SDR V1.1）可行性审查结论

| 项 | 内容 |
| --- | --- |
| 被审查文档 | `docs/软件设计报告.md`（V1.1，2026-10-21） |
| 审查类型 | 全面可行性审查（需求 / 架构 / 数据 / 流程 / 非功能 / 依赖与风险） |
| 审查结论 | **有条件通过**——整体设计方向正确、算法口径已用真实数据闭环验证，但存在 4 项致命问题（Blocker）须在开发启动前解决，7 项高风险问题须在对应里程碑前关闭 |

---

## 1. 审查总评

### 1.1 做得好的地方

1. **算法口径可信**：油耗区间判定、平均油耗、统计页九项指标均以真实导出数据跑通并与截图逐项吻合（8.13 / 0.63 / 3.06 / 3529.90 / 1.317 / 1.221 / 0.405 等），这是全报告质量最高、风险最低的部分。
2. **数据模型与存量数据对齐**：9 张实体表字段与 `manifest.json` 完全一致，`sourceId` / `updatedAt` / 软删除等跨端字段命名沿用了既有实现，迁移成本可控。
3. **需求编号体系完整**：FR/BR/NFR 编号覆盖 11 个页面、9 张表、统计口径与提醒，颗粒度足以支撑分阶段开发。
4. **已知不确定项显式化**：OI-01~OI-10 主动记录了口径差异、字段语义等模糊点，未掩盖问题。

### 1.2 主要结论

报告的**需求覆盖、数据模型、统计算法三个维度成熟度较高**；**架构的存储事务与订阅消息两个机制存在可行性硬伤**；**数据模型缺失 User/偏好实体与"购车时里程"字段，属于结构性缺口**；**编辑/删除的区间重算、充电/混动的设计落地、加密密钥管理等属于未定义或自相矛盾**。建议按第 4 节优先级排序，在 M1（基础设施）前关闭全部 Blocker，在 M4/M5 前关闭全部 High。

## 2. 分维度审查发现

### 2.1 需求覆盖

| 发现 | 判定 | 说明 |
| --- | --- | --- |
| 充电/混动仅有字段无流程与统计 | 遗漏（高） | 2.2 范围声明支持 `fuel/ev/hybrid`，但除 FR-FUEL-07 充电百分比外，无充电记录录入、电耗/每公里费用统计、混动里程分摊设计。`evMileages/hevMileages` 字段全流程无消费者。**建议 V1 收敛为"仅燃油"，ev/hybrid 字段保留但标注未实现** |
| 偏好/会员/提醒次数无需求条目 | 遗漏（高） | `remindEnabled`、`reminderSentCount`、Pro 权益、应用锁、注销账号在多处被引用，但 2.3 无对应 FR 条目，"注销账号"只在 9.2 出现，未进需求清单 |
| 隐私政策/用户协议页面 | 遗漏（中） | NFR-05 要求首次启动展示两协议，附录 A 无对应页面，11.2 也未将其列为审核交付物 |
| 编辑/删除记录的完整闭环 | 遗漏（致命） | FR-FRM-04/FR-LST-07 只到"可编辑/可删除"，未定义编辑加油记录后区间重算、编辑实付金额与 Cost 的联动 |
| 多车"当前车辆"状态 | 遗漏（中） | FR-CAR-01 有切换，但"当前车辆"如何贯穿记一笔/统计/记录页、切换后的刷新与默认值未定义 |
| "上次加油记了吗"语义 | 模糊（低） | 已列入 OI-03，但对油耗计算的影响未定义，需在产品侧敲定后回写 BR |

### 2.2 架构与模块划分

| 发现 | 判定 | 说明 |
| --- | --- | --- |
| 本地存储"事务回滚"不可行 | 错误（高） | `wx.setStorageSync` 无事务语义，7.7 声称"失败整体回滚"缺乏实现机制。记录级多 key 写入天然无原子性，可能出现"记录已写、索引未写"的孤儿数据 |
| 订阅消息"每日定时任务"不可靠 | 错误（致命） | 5.3.3 依赖"应用启动/每日定时"，但小程序无常驻定时器，纯本地优先架构无法保证每日提醒。需云函数定时触发器 + 订阅消息推送 |
| 领域层/状态层/仓储的边界 | 需澄清（中） | 7.5 由 store 创建 `localAdapter.transaction()` 再传入领域层，耦合方向可接受，但未定义"领域层能否直接依赖 adapter"的统一约束，易演变成三处各写各的 |
| 图表组件的定位 | 合理 | 组件只绘制、聚合在 `stats.service`，边界清晰，无问题 |
| 本地索引一致性对账 | 遗漏（中） | 索引与记录分 key 存储，若进程中断导致不一致，无启动时对账/重建索引机制 |

### 2.3 数据设计一致性

| 发现 | 判定 | 说明 |
| --- | --- | --- |
| 缺"购车时里程"字段 | 错误（致命） | 5.3.2 文字写"无保养记录时以**购车里程**为基线"，但 `Car` 只有 `initDate` 与 `mileages`（当前），7.4 代码基线用 `0`。三者互相矛盾，导致无保养记录项的剩余量无正确初值 |
| 缺 User/偏好实体 | 遗漏（致命） | `user.preference.*` 被 5.8/9.2/附录引用，但 4.2 无该实体，`manifest.json` 亦无。偏好、会员、提醒次数无法落库、无法导出、无法同步 |
| Cost 三来源字段无互斥约束 | 不一致（中） | BR-15 说 1:1 强关联，但 `maintainHandleSourceId/repairSourceId/fuelRecordSourceId` 允许同时非空，无 CHECK 约束 |
| FuelConsumption 的派生属性未声明 | 不一致（中） | 区间是派生数据，却与源数据同样参与同步/软删除/updatedAt，编辑源记录后会产生"派生数据 vs 源数据"双写不一致 |
| 时间戳口径未全局统一 | 轻微（低） | 5.2.2 强调 UTC+8，5.10.6 用"本地时区"，正文已基本统一但缺一句全局约定 |
| "增加总里程"的 min 口径 | 模糊（中） | BR-17 = max − min"记录里程"，未明确"记录"是否含保养/维修记录里程（样本因无维修/保养里程记录而恰好成立） |
| manifest.json 缺 user/偏好导出 | 遗漏（高） | 4.5 的 `data` 只有 9 张业务表，无偏好/会员/提醒次数，导出导入后设置丢失 |

### 2.4 关键流程与异常处理

| 发现 | 判定 | 说明 |
| --- | --- | --- |
| 编辑/删除加油记录后的区间重算规则缺失 | 遗漏（致命） | 5.2.2 只覆盖"相邻两条"的新增场景；编辑里程、删除中间一条后，原本不相邻的两条是否重配对、cost 是否联动更新均未定义 |
| 总里程与"删除不降低"矛盾 | 错误（高） | BR-12"删除记录不降低总里程"与 BR-02/BR-17 的"总里程=max(记录里程)"冲突；删除当前最大里程记录后应回到次大值 |
| 首次保养/建档基线初始化 | 遗漏（高） | 车辆建档时里程非 0（如已是 2908）时，保养项基线如何初始化未定义；仅靠"新增保养项基线=当前里程/今天"无法解释存量数据 |
| 重复提交（连点保存） | 遗漏（中） | 7.7 幂等只防 sourceId 重复，未定义按钮禁用/请求去重 |
| 历史脏数据容错 | 遗漏（中） | 样本存在 `unitPrice=0` 的记录，金额联动会产出 0 单价，无清洗/容错规则 |
| 云同步离线队列上限与重试 | 遗漏（中） | 8.1 有 sync push/pull，但离线队列容量、重试退避、失败标记均未定义 |
| 导入后的提醒次数/会员处理 | 遗漏（中） | 4.5 只重算业务数据，偏好/会员/提醒次数的导入导出策略缺失（与 User 实体缺失同源） |

### 2.5 非功能需求

| 发现 | 判定 | 说明 |
| --- | --- | --- |
| 加密密钥管理自相矛盾 | 错误（高） | NFR-04 要求 AES-256 且密钥"由用户密码/设备派生"，但小程序无稳定设备 ID，用户密码又与"打开即用"体验冲突，二者不可兼得，方案不成立 |
| 存储 10MB 上限的归档机制未设计 | 遗漏（高） | R-03 提到"超限归档到文件"，但归档读写、冷热分离、归档数据的查询降级无设计；20000 条记录约 6MB，已接近配额 |
| 冷启动 ≤1.5s 未界定范围 | 模糊（中） | 未说明是否含统计聚合；9.1 声称 2 万条聚合 ≤30ms 缺真机基准依据 |
| 埋点对非登录用户的上报策略 | 遗漏（中） | 9.3 埋点清单完整，但"异常上报到云端"对未登录/本地优先用户的触发时机未定义 |
| 隐私合规落地 | 遗漏（中） | 合规清单完整，但两协议页面、权限拒绝降级、注销数据删除的真实落点未定义 |

### 2.6 依赖与风险评估

| 发现 | 判定 | 说明 |
| --- | --- | --- |
| 订阅消息/云函数定时触发器的成本与资质 | 遗漏（高） | R-02 列了订阅消息授权，但"每日定时推送"所需的云函数定时触发器资源与成本未评估；长期订阅模板需资质 |
| 历史数据迁移路径缺失 | 遗漏（高） | 1.2 声称"历史数据零迁移"，但旧 App 用户如何把数据迁入新小程序未设计（旧 App 是否产出 .icar 格式、迁移入口与指引均无） |
| 图表自研的渲染兼容性 | 遗漏（中） | canvas 2d 在不同机型/基础库的差异、低端机降级阈值 `benchmarkLevel<10` 的依据未验证 |
| 单人开发的进度与知识孤岛风险 | 遗漏（中） | 1 人全栈 + 兼职测试 8 周，算法口径复杂且多轮返工概率高，无冗余 |
| 微信审核（类目/订阅/隐私） | 已覆盖但未单列 | 11.2 提及审核要点，但风险表未单列，建议补一条 R-09 |

## 4. 改进建议（按优先级）

### 4.1 P0 —— 开发启动前必须关闭（对应 Blocker）

1. **B-01**：`Car` 增加 `initMileages` 字段（建档时里程）；5.3.2 与 7.4 统一基线为 `lastHandle ? lastHandle.makeMileages : car.initMileages`；补充建档时里程非 0 的初始化用例。
2. **B-02**：新增 `User`（或 `Preference`）实体表，字段至少含 `remindEnabled`、`reminderSentCount`、`memberLevel/memberExpireAt`、`appLockEnabled`；纳入 4.5 导出 `data.user` 与云同步；4.2 补字段定义。
3. **B-03**：拆分"本地计算提醒队列"与"云端推送"——本地在启动/前台时计算队列，推送改为**云函数定时触发器（每日 08:00）+ 订阅消息**；明确无云环境时降级为"仅应用内提醒"，并在成本/资质评估中补充定时触发器资源。
4. **B-04**：定义统一重算规则——**任何加油记录增删改，均按时间轴全量 `rebuildConsumptions()`**；编辑实付金额时同步更新关联 `Cost.amount`；删除记录时软删并联动软删其 Cost。补充 UT 用例覆盖"删除中间一条后的重新配对"。

### 4.2 P1 —— 对应里程碑前关闭（对应 High）

5. **H-01**：BR-12 改为"总里程 = 软删除过滤后现存记录的最大里程；编辑/删除后重算"，删除与 BR-02/BR-17 的语义冲突。
6. **H-02**：放弃"事务"表述，改为明确方案二选一——(a) 写前快照 + 失败补偿删除；(b) 业务数据单文件原子整表写（`wx.setStorageSync` 整 key 覆盖天然原子）+ 索引惰性重建。补充启动时索引对账。
7. **H-03**：V1 明确**本地明文 + 系统沙箱**（openid/会员不下本地明文，仅存展示态）；真加密与密钥方案（应用锁 PIN 派生）推迟到 V2，删除 NFR-04 中不可行的表述。
8. **H-04**：云同步引入 tombstone（软删除记录在同步时传 `deleted=true`，物理清理前保留墓碑），定义删除传播时序。
9. **H-05**：V1 范围收敛为"仅燃油"，`energyType` 保留枚举但 UI 仅开放 `fuel`，充电/混动标记为 V2；或补齐充电录入与电耗统计（工作量显著，不推荐 V1）。
10. **H-06**：给出归档方案——按年分片归档到 `USER_DATA_PATH/archive/<year>.json`，当前活跃数据保留在 Storage；查询跨年时按需加载归档文件；或评估引入 wa-sqlite 作为存储底座（需重估 NFR-02）。
11. **H-07**：明确旧 App 导出格式与 .icar 的兼容性，提供迁移指引页与"旧数据导入"入口，纳入 M5 交付。

### 4.3 P2 —— 质量与一致性改进（对应 Medium/Low）

- M-01 补两个协议页面与注销入口至附录 A 与 M7 审核清单。
- M-02 加约束"三个来源字段至多一个非空"，校验在 Repository 层。
- M-03 声明 `FuelConsumption` 为派生只读，不参与同步、不参与软删除，导出时作为冗余数据带出、导入时以源数据重算为准。
- M-04 统一错误码：本地校验错误也映射到 40001 系列，定义 `ValidationError` 结构。
- M-05 明确 min 口径含所有含里程的记录类型，并更新 5.10.2 备注。
- M-06 保存按钮进入提交态禁用 + 300ms 去抖。
- M-07 导入/启动时对 `unitPrice≤0` 记录做清洗提示（补单价或标记异常）。
- M-08 定义 sync pull 分页 cursor、conflicts 对象结构（sourceId/platform/updatedAt/local/remote）。
- M-09 oilprice 限频放云函数内存缓存，额度 30 分钟/省。
- M-10 定义全局"当前车辆" store 与切换事件，各页监听刷新。
- M-11 埋点本地缓冲 + 授权后补传。
- M-12 补真机基准测试任务（M6 交付）。
- L-01 工程结构补 `i18n/`；L-02 月维度图表默认按周聚合；L-03 正文标注"区间按终点月归属为简化取舍"。

## 5. 总体结论

本设计报告**已达到进入开发评审的水平**，其统计/油耗算法与数据模型是可信的；但在以下三方面存在**结构性缺陷**，须在编码前修复：

1. **数据模型不完整**：缺 `initMileages` 与 User/偏好实体，导致保养剩余量初值、用户设置与导入导出三处无法落地（B-01/B-02）。
