### 15.2 根因（用户提供 Console 报错后确认）

```
module 'utils/chart-theme.js' is not defined, require args is './chart-theme'
    at chart-draw.ts:12
    at <require(utils/chart-draw.js)>
    at components/donut-chart/index.ts:2
```

**真实根因**：UI 打磨批次新增的 `utils/chart-theme.ts` 未被编译产出 `chart-theme.js`，而 `chart-draw.ts` 与三个图表组件都 `require` 它，于是加载即抛错 → 统计页图表组件初始化失败 → 页面渲染中断显示空白。

关键线索：`chart-draw.js` **能**加载（说明新文件本身可被编译），只是它依赖的 `chart-theme` 模块不存在。该文件用了 `as const` 断言，开发者工具内置 TS 编译插件版本较旧时可能编译失败且不产出 js，但 import 语句仍被保留。

> 此前一轮基于「WXSS 自定义属性形态」的推断**是错的**。那轮改动（令牌回退 px、阴影改字面量、TabBar 改字面量）本身是合理加固，但并非空白的原因；`custom-tab-bar` 的样式隔离问题是同期发现的**真实缺陷**，保留修复。

## 18. 渲染层报错：observers 首帧 setData 竞态（2026-11-15）

### 18.1 报错

```
[渲染层错误] Expected updated data but get first rendering data
[渲染层错误] Error: SystemError (webviewScriptError)
```

### 18.2 根因

三个图表组件的 `observers` 里**无条件调用 `setData`**：

```ts
observers: {
  'segments, total'() {
    this.setData({ activeIndex: -1 });   // ← 首帧前调用
    this.draw();
  }
}
```

自定义组件的 `observers` 在**首次接收属性**时就会触发，**早于 `ready()` 生命周期**。此时首次渲染尚未完成，`setData` 会与首帧数据竞争，渲染层即报 `Expected updated data but get first rendering data`。

统计页的图表用 `wx:else` 条件渲染（`<donut-chart>` / `<line-chart>` / `<bar-chart>`），组件在数据到位后才创建，属性一次性传入 → 必然命中该竞态，因此报错稳定复现。

> 该写法是历史遗留（`6820491` UI 打磨批次已存在），非本轮引入。

### 18.3 修复

| 项 | 处理 |
| --- | --- |
| 三个图表组件 | `observers` 增加 `_ready` 守卫：未就绪直接 return，**初始绘制统一交给 `ready()`**；就绪后仅在 `activeIndex !== -1` 时才 `setData`（避免无意义重渲染） |
| 回归防护 | 新增 `tests/component-lifecycle.test.ts` 7 用例：断言三个组件的 observers 块内 `_ready` 守卫出现在 `setData` 之前、`ready()` 中标记 `_ready` 并绘制、`icon-picker` 不使用 observers |

**已排除**：`onLoad` 中的 `setData`（首帧前的标准同步赋值，不会触发此错误）、`custom-tab-bar` 与 `icon-picker`（无 observers）。

**验证**：typecheck 无错误、**25 套件 / 227 用例全绿**、lint 无告警。

### 18.4 经验

自定义组件里凡是「属性变化 → setData → 重绘」的模式，**首次属性注入与后续属性变化必须区分对待**。判定方式统一为在 `ready()` 里置 `_ready = true`，`observers` 首行守卫。这条已写入第 11.5 节的组件约定。

### 20.5 修复：分栏气泡过高、文字贴上沿（用户反馈，同日）

**现象**：图标选择器的 5 个分栏，气泡明显比文字高很多，文字贴着气泡上沿。

**根因**：`.tab` 只设了 `padding: 12rpx 24rpx`，**没有 height 也没有 line-height**。它是 `scroll-view`（`enable-flex`）的 flex 子项，父容器默认 `align-items: stretch`，气泡被拉高到容器的行盒高度，而内部单行文字按块级行盒**顶对齐**，于是贴在气泡上沿。

**修复**：

| 项 | 改前 | 改后 |
| --- | --- | --- |
| `.tab-bar` | `display:flex`（无高度、无对齐） | `align-items:center` + `height:64rpx` |
| `.tab` | `padding:12rpx 24rpx`（无定高） | `height:56rpx` + `padding:0 24rpx` + `display:flex; align-items:center` + `line-height:1` |

关键点：**用 flex 居中而不是靠 padding 或 line-height 撑**。文字垂直居中不再依赖字体默认行高，也不会被子项 stretch 影响——即使父容器高度变化，气泡高度和文字位置都不变。

容器比 chip 高 8rpx，留出居中余量，避免恰好等高时边缘被裁。

**验证**：typecheck 无错误、30 套件 317 用例全绿、组件 WXSS 无内联 hex。另附 `docs/prototype/icon-picker.html` 修复前后对比页（数值按 1rpx = 0.5px 换算）。

### 20.6 二次修复：分栏横向不能滑动、气泡顶部被裁（用户复测反馈，同日）

20.5 的修复只解决了「文字贴顶」，但复测发现两个新问题：**左右无法滑动**、**气泡顶部被遮掉一点**。两者同源——`scroll-view` 在 `enable-flex` 下不可靠：

| 现象 | 机制 |
| --- | --- |
| 横向滑不动 | `scroll-view` 设了固定高度 + `display:flex` 后，内部滚动容器宽度未被撑开，`scroll-x` 不生效 |
| 气泡顶部被裁 | `scroll-view` 自带 `overflow:hidden`，气泡若略高于容器就被切掉顶部，看起来像「被上面遮住」 |

**根因判断修正**：20.5 认为问题在 `stretch` 拉伸，实际主因是 `scroll-view` 的裁切。

**最终修复：不用 scroll-view。**

先测算是否真的需要滚动（面板可用宽 = 750 − 32×2 = 686rpx）：

| chip 内边距 | 5 个分栏总宽 | 结论 |
| --- | --- | --- |
| 24rpx（原值） | 712rpx | **溢出 26rpx** ← 这就是当初上滚动的原因 |
| 20rpx | 672rpx | 放得下，但只余 14rpx，太紧 |
| **16rpx** | **632rpx** | 放得下，余 54rpx ✅ |

因此把内边距收到 16rpx，改用普通 `view` + `flex-wrap`：

- 不需要滚动 → 「滑不动」问题消失
- 没有 `overflow:hidden` → 气泡不再被裁
- `flex-wrap` 仅作兜底：个别机型 CJK 字宽略大于字号时自动换行，不溢出

**教训**：给横向排列加 `scroll-view` 前，先算一下总宽是否真的超出。若只是差一点点，收窄内边距比引入滚动更稳——滚动容器带 `overflow:hidden`，一旦内部高度与容器不完全一致就会静默裁切，而且 `enable-flex` 下的滚动行为在不同基础库版本上表现不一致。

**验证**：typecheck 无错误、30 套件 317 用例全绿、组件 WXSS 无内联 hex。对比原型 `docs/prototype/icon-picker.html` 已更新为最终方案。

### 20.7 三项改进：两字标签 / 固定高度 / 自定义分栏（用户需求，同日）

**1. 分栏标签改为两字**

`加油充电 → 能源`、`洗美维修 → 养护`、`通行规费 → 通行`、`车型车色 → 车型`，加上「其他」与新增的「自定义」，共 6 个分栏。

改名同时解决了溢出：4 字标签时 5 个分栏合计 712rpx，超过面板可用 686rpx；2 字标签后 6 个分栏只有 600rpx，余 86rpx，单行放得下。

**2. 切换分栏时面板高度跳动**

原因：`.icon-scroll` 用的是 `max-height: 560rpx`。各分组图标数不同（能源 6 个、养护 15 个），内容短的把面板撑矮，于是上下跳。

修复：改为**固定 `height: 208rpx`**，正好两行（每行 88 + 8×2 = 104rpx），超出则内部滚动。自定义分栏的空态也强制 208rpx，避免切到空分栏时面板突然变矮。

> 测试里加了两条断言：`.icon-scroll` 必须有 `height: 208rpx` 且**不得出现 `max-height`**——防止以后有人改回去。

**3. 新增「自定义」分栏**

用户上传的图标需要集中管理，否则每次都要重新上传。新增 `customIcons` 表与 `services/custom-icon.service.ts`：

| 接口 | 作用 |
| --- | --- |
| `addCustomIcon` | 裁剪完成后登记（按路径去重，重复选择不新增） |
| `listCustomIconPaths` | 供分栏展示，最近上传的在前 |
| `removeCustomIcon` | 长按删除，**物理删除** |

**为什么用物理删除**：图标登记不是业务数据，软删会让回收站出现一堆「自定义图标」条目，恢复后还是同一个文件，没有意义。

**两个关键约束**：

1. **不参与数据导出**。导出的只是 `wxfile://` 路径，换设备后文件不存在，带过去只会得到一堆点不开的空白图标。
2. **必须进入启动清理的保留集**。否则孤儿清理会把用户的图标库当成无主文件删掉——`utils/icon-store.ts` 的保留集已从「实体引用的图标」扩展为「实体引用的图标 ∪ 登记表」（有测试锁定）。

**其它细节**：
- 组件用 `lifetimes.attached` 读取登记表，**不用 `observers`**——observers 在首次属性注入时就会触发，是之前修过的首帧 setData 竞态来源（`component-lifecycle.test.ts` 也断言 icon-picker 不得出现 observers）。
- 始终默认停在第一个预设分栏，不因为「有自定义图标」就擅自跳过去，否则用户会找不到预设图标。
- 自定义图标用 `<image mode="aspectFill">` 渲染并强制 88rpx 方形，避免原图比例把格子撑变形。

**验证**：typecheck 无错误、**31 套件 / 335 用例全绿**（新增 `tests/custom-icon.test.ts` 18 用例）、lint 无告警。原型 `docs/prototype/icon-picker.html` 更新为四场景对比（能源一行 / 养护三行滚动 / 自定义有内容 / 自定义空态），四个面板高度一致。

### 23.7 保养栅格：三列固定尺寸，最多两行、超出滚动（同日）

需求确认过程：最初是三列自动换行不限高 → 误做成两列 → 最终定为**三列 + 最多两行 + 超出滚动 + ≤3 项只占一行**。

| 项 | 值 | 推算 |
| --- | --- | --- |
| 卡片内宽 | 638rpx | 750 − 页面 padding 24×2 − 卡片 padding 32×2 |
| 单元格宽 | **200rpx** | 3×200 + 2×16 = 632 ≤ 638 |
| 单元格高 | **156rpx** | 20 + 44(图标) + 10 + 34(名称) + 6 + 28(周期) + 14 |
| 两行可视高度 | **328rpx** | 156×2 + 16，即 6 项 |
| 一行高度 | 156rpx | ≤3 项时随内容收缩，不加定高 |

**列宽为什么取 200 而不是精确的 202**：`(638 − 32) / 3 = 202` 正好铺满，但总宽恰好等于容器时，亚像素舍入可能让第 3 个掉到下一行。取 200 留 6rpx 余量，视觉上无差别。

**定高是有条件的**：只在 `maintains.length > 3` 时加 `*-scroll-fixed`。≤3 项时只有一行，若强制 328rpx 会留一大片空白。

**名称与周期必须写显式 `line-height`（34/28rpx）**：不写就依赖字体默认行高，单元格高度会随内容浮动，`156rpx` 与 `328rpx` 的推算全部失效，滚动区可能露出半行。

- **规范名已存在** → 每个别名类别的支出改指向规范类别，别名软删
- **规范名不存在** → 取第一个别名**原地改名**，其余并入它

**原地改名而不换 `sourceId`**：支出记录靠 `sourceId` 关联；换 id 就要迁移全部历史支出且容易漏。`sourceId` 对用户不可见，改名不影响任何展示，历史支出自动跟着走。

`dedupePresetCategories` 仍先跑，处理「同一名字的多条预设」；`normalizePresetName` 处理「不同名字指向同一语义」。两者职责不重叠。

### 25.3 关于「其余类别归进自定义」

实现上**不做任何迁移**：四个支出预设之外的类别，本来就只有两种情况——

- 用户自建的自定义类别（`isPreset=false`），保持原样
- 系统预设（加油/充电/保养/维修），由专用表单自动生成流水，**必须保留**，删了会让这些支出归到「其他」

若此处理解有偏差（比如希望把某类支出批量改挂到自定义类别），需要再确认。

### 25.4 测试与数据

- `tests/category-presets.test.ts` 的「旧库升级」用例重写为 4 个场景：只有「停车费」→ 原地改名；「停车」与「停车费」并存 → 支出全部归并到「停车」；「高速费」→「高速」；两者并存 → 归并到「高速」
- 排序用例的期望顺序同步为 `停车 / 高速 / 保险 / 洗车`
- `tests/cost.service.test.ts` 里作为**自定义类别**夹具的「停车费」全部改名为「快递费」，避免与归并别名混淆（否则触发归并会把夹具吃掉）
- `test-data/generate.py` 的预设与 `CAT` 映射同步；三个样本 JSON 重新生成

**验证**：typecheck 无错误、**34 套件 / 426 用例全绿**、lint 无告警。

## 26. 支出类别管理合并为一组，预设只初始化一次（2026-11-16）

### 26.1 需求

「支出类别管理」不再分「预设 / 自定义」两段，合并为一个列表，**每项操作完全一致**（改图标、改名、删除、显示开关、拖动排序）。

### 26.2 关键：只改 UI 会出两个 bug

| 操作 | 只改 UI 的后果 |
| --- | --- |
| 删除预设 | `seedPresetCategories` 每次启动都按名字补建 → **删了又回来** |
| 改名预设 | 原名被当成「缺失」而补建 → **两个类别并存**，旧支出还挂在被改名的那个上 |

因此必须同时改数据层。

### 26.3 方案：支出预设只初始化一次

`User` 新增 `categoriesSeeded`，启动时：

| 类别 | 策略 |
| --- | --- |
| **系统预设**（加油/充电/保养/维修） | **无条件确保存在**。用户看不到它们，无法自行恢复，而 `refuel` / `maintain-record` / `repair` 靠 `presetType` 找类别，缺失即功能不可用 |
| **支出预设**（停车/高速/保险/洗车） | 仅在 `categoriesSeeded` 为空时创建一次，之后**完全交给用户**：删掉的不重建、改过名的不再冒出原名 |

老用户升级时该字段为空，会完整跑一次初始化（归并曾用名 → 补建预设 → 重排 `sortOrder` → 打标记），行为与之前一致。

### 26.4 一并调整的三处

**1. 排序改为单一序列**

`listCategories` 原按「预设在前、组内按 sortOrder」排。合并分组后若保留，用户把预设拖到自定义项下面会**立刻弹回原位**。改为纯 `sortOrder` 排序（同号按创建时间），并在首次初始化时调用 `renumberSpendCategories` 把两套独立编号（预设 0-3、自定义 0-1…）重排为单一 0..n-1，**按当前视觉顺序重排，用户看不出变化**。

**2.  dragged 兄弟集扩大**

`moveCategory` / `moveCategoryBy` 的兄弟集从「同 isPreset 分组」改为「全部非系统预设」，这样预设与自定义可以互相换位。对系统预设调用直接返回 false。

**3. 服务层放开限制**

| 函数 | 改前 | 改后 |
| --- | --- | --- |
| `removeCategory` | 预设一律拒绝 | 支出预设可删；系统预设拒绝（提示「系统分类不能删除」） |
| `updateCategory` | 预设改名无效（静默 return） | 支出预设可改名；系统预设仍拒绝 |

### 26.5 导入路径

`io.service` 导入后原本只调 `dedupePresetCategories`。由于启动时的曾用名归并已被标记挡住，**导入必须自己再补一次** `normalizeSpendCategoryAliases`，否则旧备份里的「停车费 / 高速费」会和本地「停车 / 高速」并存。

### 26.6 测试

`tests/category-presets.test.ts` 新增 6 条：

- 首次 seed 写入 `categoriesSeeded`
- **删除预设后再 seed 不重建**
- **重命名预设后不再冒出原名**
- 系统预设被删后仍自动补建（不受标记约束）
- 二次 seed 不改动既有顺序
- 老库升级只跑一次初始化

`tests/cost.service.test.ts` 调整 4 条旧断言：支出预设可删 / 系统预设不可删、新增类别接在支出序列末尾（从 4 开始）、拖动可跨越预设与自定义、批量换位后**整个支出序列**的 sortOrder 连续。

> 反例验证：让 seed 忽略 `categoriesSeeded` 后，「删除不重建」「改名不复活」「老库只跑一次」3 条立即变红；恢复后转绿。

**验证**：typecheck 无错误、**34 套件 / 432 用例全绿**、lint 无告警。原型 `docs/prototype/category-manage.html`。

## 27. 导入方式交给用户选择：合并 / 覆盖（2026-11-16）

### 27.1 问题

导入一直是**纯 upsert**（逐条 insert/update，从不删记录）。配合第 26 节「预设只初始化一次」后，暴露出一条明显的不一致：

> 旧手机上删掉了「洗车」→ 导出备份 → 换新手机导入 → **「洗车」还在**（因为新机启动时 seed 已经建过，而导入不删本地）

### 27.2 方案：导入时让用户选

`importBundle(storage, json, mode: 'merge' | 'replace')`，默认 `merge`（兼容既有调用）。

| 方式 | 行为 | 适用 |
| --- | --- | --- |
| **合并** `merge` | 同 id 按 `updatedAt` 较新者覆盖，本地多出的记录**保留** | 把另一台设备的数据并进来 |
| **覆盖** `replace` | **先物理清空**业务表与派生表，再整份写入 | 换机恢复、想得到与备份完全一致的状态 |

**不清 user**：`openid` / 会员 / 置顶 / `categoriesSeeded` 都是本机属性。尤其 `categoriesSeeded` 若被清掉，下次启动会把用户删过的预设**重新建出来**——正好抵消第 26 节。

清表用 `hardDelete` 而非软删：软删会留下回收站条目，且 `list` 不过滤 `deleted`，会让后续统计读到脏数据。

### 27.3 交互

`pages/data-transfer` 导入时先弹 `showActionSheet`：

- 合并导入（保留现有数据）
- 覆盖导入（清空现有数据）

选「覆盖」后**再弹一次确认**（红色「仍要覆盖」），文案明确「不可撤销，建议先导出当前数据」。用户取消选择则不提示。

结果提示也区分：覆盖显示「覆盖完成：写入 N 条」，合并显示「合并完成：新增/更新/跳过」。

### 27.4 测试

`tests/io.service.test.ts` 新增 6 条：

- 合并：本机多余记录保留，备份记录并入
- 覆盖：本机多余记录被清掉
- 覆盖：**备份里用户删过的预设不会被 seed 重建**
- 覆盖：本机 user 属性（置顶 / 会员 / 已初始化标记）不被覆盖
- 覆盖：车辆数据完整写入并重建派生数据
- 不传 mode 时仍是合并（兼容）

> 反例验证：把覆盖模式的清表改成空操作后，「本机多余记录被清掉」「被删过的预设不会重建」2 条立即变红；恢复后转绿。

**验证**：typecheck 无错误、**34 套件 / 438 用例全绿**、lint 无告警。

## 28. 备份不打包图标，恢复时换成预设图标（2026-11-16）

### 28.1 问题

实体上的 `icon` 存的是本机沙盒路径（`wxfile://usr/icon-1699999999999.png`）。导出的是 JSON，**不含文件本身**，所以换机或在新设备导入备份后，所有自定义图标必然失效；而 `isImageIcon` 只看后缀 `.png` 就判定为图片，`<image>` 加载失败 → **裂图**。

涉及车辆、类别、保养项三处，出现在主界面 Hero、车辆列表、记录列表、保养栅格等多个界面。

### 28.2 结论：不打包图标

一度实现过「可选把图标转 base64 一并导出」（方案 C），随后被否掉：

> 每个小程序本身都有预设图标，恢复备份时给它一个默认的预设图标就够了，没必要为装饰性数据把备份撑大。

| 方案 | 备份体积 | 换机后 |
| --- | --- | --- |
| ~~打包 base64~~ | 每个图标 +40KB，几十个就几 MB | 图标完整恢复 |
| **不打包（最终）** | 不变 | 换成对应预设图标 |

### 28.3 恢复时按实体类型给预设图标

`DEFAULT_ICON_BY_TABLE`：

| 表 | 预设图标 |
| --- | --- |
| `cars` | 🚗 |
| `categories` | 🧾 |
| `maintains` | 🔧 |

**为什么不能统一回落 📌**：`displayIcon('')` 的兜底是 📌，给「保养项」配 📌 会让人以为数据出错。按实体类型给图标，恢复后的界面才符合直觉。

`resolveIcon(raw, table)` 的分支：

| 情况 | 结果 |
| --- | --- |
| emoji 类图标（预设） | 原样保留 |
| 自定义图片图标，本机已有同文件 | 继续用本地路径（同机合并不误伤） |
| 自定义图片图标，本机没有 | 换成该表的预设图标 |
| 原本就是空 | 补上该表的预设图标 |

### 28.4 清理

方案 C 引入的 `readIconBase64` / `writeIconBase64` / `ICON_EXPORT_MAX_CHARS` / 导出页开关全部移除，`manifest.icons` 与 `imageMode: 'base64'` 也不再产生。`imageMode` 恒为 `file`。

### 28.5 测试

`tests/icon-transfer.test.ts` 9 条，用桩 `wx` 模拟沙盒：

- 备份里没有 `icons` 字段、`imageMode` 恒为 `file`、内容不含 base64 数据
- 换机后按表换成 🚗 / 🧾 / 🔧（不是统一 📌）
- 导入后不再残留任何 `icon-*` 失效路径
- 本机已有同文件时保留本地路径
- emoji 类图标不受影响
- 原本为空的补上预设图标
- 导出页不再有图标开关，两个导出入口都不传选项

> 反例验证：把「按表取预设图标」改成统一返回空后，「按实体类型换成预设图标」「原本为空的补上预设图标」2 条立即变红；恢复后转绿。

**验证**：typecheck 无错误、**35 套件 / 447 用例全绿**、lint 无告警。

> 本节解决了第 21.3 节记录的第 12 项（换机后自定义图标全部裂图）。

## 29. 备份改为「只走文件」，并修复导出文件失效（2026-11-16）

### 29.1 导出文件为什么「失效」

`wx.shareFileMessage` 有两个硬限制，原实现都没处理：

| 限制 | 后果 |
| --- | --- |
| **微信开发者工具不支持**，调用必然进 `fail` | 在开发者工具里点「导出为 JSON 文件」只会弹「分享失败」，看起来就是功能坏了 |
| 基础库需 **≥ 2.16.1** | 低版本微信直接失败，且没有任何提示 |

原代码把 `fail` 的提示写成「分享失败，请改用复制方式」—— 而复制入口随后又被删掉了，用户彻底没有出路。

### 29.2 修复

| 项 | 处理 |
| --- | --- |
| 开发者工具 | `getSystemInfoSync().platform === 'devtools'` 时直接弹窗说明「请在真机上导出」，不去调用必然失败的接口 |
| 低版本微信 | `wx.canIUse('shareFileMessage')` 判断，提示升级 |
| 写入校验 | 写文件后用 `accessSync` 确认真的落盘，再调分享 —— 否则只会拿到模糊的 fail |
| 用户取消 | `errMsg` 含 `cancel` 时不弹错误（取消是正常交互） |
| 分享失败兜底 | 弹窗引导「保存到手机」（`wx.saveFileToDisk`），文件已在本机，用户仍能拿走 |
| 选文件不限定扩展名 | 部分机型转发后后缀会被改写，限定过严会让用户「明明选了文件却说没选到」；内容校验交给 `importBundle` |

### 29.3 只保留文件方式

按需求去掉「导出并复制」与「粘贴导入」：

- JSON 动辄几十上百 KB，剪贴板既容易截断，用户也很难可靠保存与再次找到
- 文件可长期留在聊天记录里（建议发「文件传输助手」），是更稳的载体

**关于文件格式**：继续用 `.json`。它是纯文本、跨平台、任何编辑器都能看，也方便用户自己核对内容；换成 `.zip` 需要额外压缩库，而这个数据量（几百 KB）压缩收益有限，反而增加解压失败的可能。真正该改的是**载体**（从剪贴板换成文件），而不是格式。

### 29.4 测试

新增 `tests/data-transfer-page.test.ts` 11 条：

- 页面不再有「导出并复制」「粘贴导入」与 textarea；逻辑里无 `setClipboardData` / `jsonText` / `onInput`
- 保留「导出备份文件」与「选择备份文件」两个入口
- 开发者工具中弹窗而非调用；低版本走 `canIUse`
- `writeFileSync` → `accessSync` → `shareFileMessage` 的**顺序**必须成立
- 取消分享不弹错；失败时提供「保存到手机」
- 选文件不限定 extension；合并/覆盖仍区分且覆盖需二次确认
- 无 `.json-input` 残留样式、无内联 hex

> 反例验证：删掉开发者工具检测后，「开发者工具中直接提示改用真机」断言立即变红；恢复后转绿。
>
> 写测试时踩了一个坑：最初用 `indexOf('shareFileMessage')` 判断顺序，结果命中了前面 `canIUse` 里的同名文本，断言恒真。改为比对实际调用 `wx.shareFileMessage({` 才有意义。

**验证**：typecheck 无错误、**36 套件 / 458 用例全绿**、lint 无告警。

### 29.5 二次修复：「保存到手机」在手机上必然失败（用户真机反馈）

**现象**：真机上导出成功、文件能发到「文件传输助手」，但点「保存到手机」提示失败。

**根因（平台限制，不是代码 bug）**：

| 接口 | 限制 |
| --- | --- |
| `wx.saveFileToDisk` | 官方原文：**「仅在 PC 端支持」**（Windows / Mac 微信）。手机上调用必然进 `fail` |
| `wx.openDocument` | `fileType` 白名单只有 `doc/docx/xls/xlsx/ppt/pptx/pdf`，**不含 json / txt**，无法预览备份文件 |

小程序运行在沙箱内，**没有任何 API 能把文件写进手机的系统文件管理器**。这不是没找对接口，是微信不给这个能力。

**修复：按平台分流，不给用户不可能的预期**

| 平台 | 按钮文案 | 行为 |
| --- | --- | --- |
| PC 端 | 保存到电脑 | `wx.saveFileToDisk` 弹系统「另存为」 |
| 手机端 | **再次发送备份** | `wx.shareFileMessage` 再调一次分享，把文件发到聊天记录 |

手机端页面上补一句说明：「手机上无法直接写入文件管理器（微信限制）。建议把备份发到『文件传输助手』长期保存。」

**另外两处改动**：

- **按钮常驻**：导出后把文件路径写入 `Storage`（`icar:last-backup`），重进页面时用 `accessSync` 校验后恢复显示；文件被系统回收则自动隐藏
- **文件失效兜底**：点按钮前 `accessSync` 校验，失效时明确提示「备份文件已被系统清理，请重新导出」并清空按钮

**测试**：`data-transfer-page.test.ts` 增至 17 条，新增：

- PC / 手机端文案与分支正确，`saveFileToDisk` **只在 PC 分支**调用
- 手机端走 `reshare`（`shareFileMessage`）
- 页面不再出现「保存到手机」字样
- 按钮常驻（`setStorageSync` / `getStorageSync`）
- 文件失效时提示并清空
- 不调用 `openDocument`（json 不在白名单）

> 反例验证：让手机端也走 `saveToDisk`（即恢复上一版的错误做法）后，「saveFileToDisk 只在 PC 分支调用」立即变红；恢复后转绿。
>
> 写测试时踩了两个坑：① `indexOf('openDocument')` 会命中注释里的同名文字，改为匹配 `wx.openDocument\s*\(`；② WXML 里按钮文案是 `{{saveLabel}}` 变量，断言字面量「再次发送备份」找不到。

**验证**：typecheck 无错误、**36 套件 / 464 用例全绿**、lint 无告警。

## 31. 裁剪页视口变化后取景偏移（2026-11-16）

### 31.1 问题

`pages/icon-crop` 只在图片加载后**测量一次** `boundingClientRect` 得到视口边长，之后一直用它换算裁剪区域。

转屏、分屏、折叠屏展开、键盘弹出都会改变视口像素边长。一旦变化，`viewportSize` 就与实际不符，`computeSourceRect` 算出的取样矩形整体偏移——**用户看到的取景与裁出来的图不一致，而且肉眼很难察觉**（导出的图看起来「正常」，只是不是他要的那块）。

### 31.2 改法

**1. 新增纯函数 `resizeViewport(state, src, prevVp, nextVp)`**

把「取景迁移」抽成可测逻辑：

- 先算旧视口中心对应的**图片内坐标**（相对图片左上角的像素）
- 再反解出「让新视口中心仍对准同一处内容」所需的新偏移
- 最后 `clampOffset` 夹回合法区间，保证不露白边

第一版实现写错了：直接按「视口中心变化量」平移 `dx = (next - prev) / 2`，且**横纵用同一个 dx**。横图在纵向本就有留白（被夹紧），强行平移会让取景跳到 0.375 而不是 0.5。测试直接抓到了这个错误。

**2. 页面接上尺寸变化监听**

- `initViewport` 首次测量成功后调用 `watchResize()`
- `wx.onWindowResize` 触发后**重新实测** `boundingClientRect`（不直接用回调里的窗口宽高，避免与视口实际尺寸不一致）
- 变化小于 0.5px 时忽略，避免连续 resize 抖动
- `onUnload` 里 `wx.offWindowResize` 解绑，防止页面销毁后回调仍持有引用

### 31.3 测试

新增 `tests/crop-resize.test.ts` 11 条：

- 视口变大 / 变小：取景中心在源图上的相对位置**保持不变**（误差 < 0.0005）
- 缩放比例在视口变化时不变
- 4 档视口 × 3 档缩放组合下，图片始终完全覆盖视口（无白边）
- 旧 state 越界时能被夹回（不继承非法偏移）
- 视口相同则状态不变（幂等）
- 横图、竖图都成立
- 非法输入安全降级
- 页面确实监听并解绑了尺寸变化，且监听在首次测量之后才启动

> 反例验证：把 `resizeViewport` 退化为「只夹紧、不迁移取景」后，「视口变大/变小取景不跳」「横竖图都成立」3 条立即变红；恢复后转绿。

**验证**：typecheck 无错误、**38 套件 / 483 用例全绿**、lint 无告警。

## 38. 「推荐给朋友」文字居中加粗的修复（2026-11-16）

### 38.1 现象

「把车记本推荐给朋友」的文字**居中且加粗**，箭头紧贴文字而不是靠最右，
与上方「反馈与建议」「关于」等选项明显不一致。

### 38.2 根因：微信给 `<button>` 注入了内置默认样式

代码本身写得没错（已声明 `text-align: left`、`display: flex`、
`justify-content: space-between`），但微信给 `button` 注入了：

| 内置样式 | 导致的现象 |
| --- | --- |
| `text-align: center` | 文字居中 |
| `font-weight: bold` | 文字加粗 |
| `display: block` | 设的 `display: flex` 被干扰，`space-between` 失效 → 箭头紧贴文字 |

**这些内置样式优先级高于普通 class 选择器**，所以只靠 class 覆盖并不可靠。
这是小程序 `button` 的经典坑。

### 38.3 改法：button 只当壳，布局交给内层 view

```wxml
<button class="share-btn" open-type="share" hover-class="hover-dim">

    <view class="row-label">把车记本推荐给朋友</view>
    <view class="row-arrow">›</view>
  </view>
</button>
```

```css
/* button 上显式重置三项内置样式 */
.share-btn {

  font-weight: normal;   /* 重置加粗 */
  text-align: left;      /* 重置居中 */
  line-height: normal;
  margin: 0 calc(0rpx - var(--sp-4));  /* 抵消 .card 内边距 */
  padding: 0;            /* 内边距移到内层，避免双重 */
  background: transparent;
  border: none;
  border-radius: 0;
}
.share-btn::after { border: none; }    /* 去掉 button 默认边框 */

/* 内层承载布局，不受 button 内置样式影响 */
.share-inner {
  display: flex;
  align-items: center;
  justify-content: space-between;   /* 箭头自然到最右 */
  min-height: 104rpx;
  padding: 0 var(--sp-4);
}
```

### 38.6 第一次修复失败：在 button 上覆盖样式在真机不生效

第 38.3 节的方案（button 当壳 + 内层 view 布局 + 在 button 上写
`font-weight: normal` / `text-align: left` 重置）**在真机上没有效果**，
文字仍然居中加粗。

原因：微信对 `button` 的渲染干预比预想的深，注入的 `text-align`、`font-size`、
`padding`、`line-height` 等即使写了 class 覆盖，真机上仍可能不生效。
**「覆盖内置样式」这条路本身不可靠。**

### 38.7 最终方案：button 只做透明覆盖层

不再试图把 button 改造成普通行，而是**把它的视觉影响彻底隔离出去**：

```wxml
<view class="card">
  <view class="row row-share">
    <view class="row-label">把车记本推荐给朋友</view>
    <view class="row-arrow">›</view>
    <!-- 铺满整行的透明覆盖层，只负责触发分享 -->
    <button class="share-cover" open-type="share" hover-class="none" />
  </view>
</view>
```

```css
.row-share {
  position: relative;   /* 给覆盖层提供定位参照 */
}
.share-cover {
  position: absolute;
  left: 0;
  top: 0;
  width: 100%;
  height: 100%;
  opacity: 0.01;        /* 不可见但可点击 */
  z-index: 1;
  padding: 0;
  margin: 0;
  border: none;
  background: transparent;
}
```

**关键点**：

1. **视觉复用 `.row` / `.row-label` / `.row-arrow`** —— 与上面「关于」是
   同一套类，字号、字重、左对齐、箭头位置**必然一致**，不是「凑」出来的
2. **button 内部不放任何内容**（自闭合），它的内置样式无处作用
3. **`opacity: 0.01` 而不是 `0`** —— 部分渲染引擎下 `opacity: 0` 的元素
   可能不接收点击事件，会导致分享面板调不起来

这是「隔离」而非「覆盖」的思路：既然改不动 button 的样式，就让它只承担
「被点击」这一件事。

### 39.6 数值格式化规则（`utils/num-format.ts`）

图块太窄，需要「先压缩、再降字号、绝不省略」：

| 金额 | 显示 |
| --- | --- |
| < 10 万 | 完整千分位 `￥28,450`（记账要精确值） |
| 10 万 ~ 1 亿 | 万，小数位按量级 **2/1/0** 递减 |
| ≥ 1 亿 | 亿 |

里程同规则、阈值同为 10 万，**单位 km 永不丢弃**。

**小数位递减**是保证数字部分 ≤ 6 字符的关键：

| 万值 | 小数位 | 例 |
| --- | --- | --- |
| < 100 | 2 | `12.85万` |
| 100~999 | 1 | `123.5万` |
| ≥ 1000 | 0 | `1235万` |

**两个必须处理的细节**：

1. **去尾 0**：`12.80万 → 12.8万`。尾 0 白占 1~2 个字符宽度，是溢出主因。
2. **不能直接用 `toFixed`**：`128.45` 在二进制里是 `128.4499…`，
   `(128.45).toFixed(1)` 得 `"128.4"`。用户看到 128,450 变成 128.4 万会认为算错，
   因此加 `1e-9` 偏移再取整（`roundTo`）。

**字号回退**：按 `11.5→11→10.5→10→9.5→9→8.5` 逐档试，取能放下的最大者；
两列**取较小值统一**。经全量级验证（0 ~ 1e12），所有情况在 10px 以上都能放下。

**每公里成本**：

| 情况 | 显示 |
| --- | --- |
| 常规 | `￥0.61` |
| < 0.01 | `￥0.008`（3 位，否则显示成 0.00） |
| ≥ 10 | `￥12.5`，封顶 `￥99.9` |
| **里程 = 0** | **`￥--`**（拦截除零，绝不出现 Infinity/NaN） |

```ts
export function safeBack(ctx: any, delay = 600): void {
  setTimeout(() => {
    if (typeof getCurrentPages !== 'function') { wx.navigateBack(); return; }
    const pages = getCurrentPages();

}
```

## 44. 第 3 批：覆盖导入可回滚 + 概览汇总去 O(车×记录)（2026-11-17）

### 44.1 S1：覆盖导入原来是「先清空后写入」

```ts
if (mode === 'replace') cleared = clearTables(...);   // 旧数据此刻已没了
for (table of TABLES) { for (e of data[table]) storage.insert(...) }  // 中途抛错就两头空
```

本地 Storage 没有事务，`catch` 只返回「数据可能未完整导入」——
用户既没有新数据、也没了旧数据。

**第一次改法只做对了一半**：把「净化 + 图标回落 + 引用校验」前置到清空之前。
但这只挡得住**校验阶段**的失败，**写入阶段**照样会抛错（存储配额满、某条数据触发适配器异常）。
反例验证时发现了这一点：把清空挪回原位，行为断言竟然没红。

**最终做法：两段式 + 回滚快照**

| 阶段 | 动作 |
| --- | --- |
| 1. 暂存 | 逐表 `sanitizeImported` + 图标回落，得到 `staged`（内存里） |
| 2. 校验 | 断开悬空的**次级引用**（见 44.2） |
| 3. 快照 | 清空前把各表逐条**浅拷贝**存进 `backupRaw` |
| 4. 清空 | `clearTables` |
| 5. 落库 | 写 `staged` |
| 6. 失败 | `catch` 里用快照写回，返回「导入失败，**已恢复到导入前的数据**」 |

为什么用「逐条浅拷贝」而不是 `exportBundle`：
`exportBundle` 只导未删项，而覆盖导入清的**包含回收站里的软删记录**，
用它做快照会把回收站内容永久丢掉。

为什么浅拷贝而不是直接存引用：适配器 `list()` 返回的是库里对象的引用，
落库阶段的 `update` 会就地改掉它，快照必须是真的副本。

### 44.2 引用完整性：断次级引用，但不动 `carSourceId`

备份里可能有指向不存在实体的记录（手改过、跨版本）。直接写进去会形成
「看不见的孤儿」：支出的类别不存在 → 页面回落成「其他」但统计里仍占一份金额；
加油记录的 `costSourceId` 悬空 → 油费进了 `fuel.totalCost` 却不进 `expense.total`。

处理方式是**清空该字段**（`categorySourceId` / `maintainSourceId` / `handleSourceId` /
`costSourceId` 等），记录本身保留 —— 金额、日期、里程仍然有价值。

**刻意不处理 `carSourceId`**：

- 丢弃整条会**静默损失用户数据**（导入本来就是为了保住数据）
- 清成空串只会让它更没意义
- 原样保留，等对应的车之后被导入时还能自动归位

> 这一点是反例验证纠正过来的：初版把「没有 carSourceId 的记录」直接丢掉，
> 导致 `io.service.test.ts` 与 `audit-fixes.test.ts` 里两条既有用例变红 ——
> 它们构造的正是无 `carSourceId` 的合成记录。这说明「丢弃」是过度设计。

## 46. 服务层错误处理统一（2026-11-17）

### 46.1 改造前：三种方式并存，且错误信息到不了用户

| 方式 | 例子 | 问题 |
| --- | --- | --- |
| `throw new Error('记录不存在')` | `updateCost` / `updateRepair` / `updateRefuel` / `updateMaintainHandle` / `saveRefuel` | **message 完全没人读** |
| 返回 `{ ok, message }` | `removeCategory` / `clearAllData` / `importBundle` | 调用方需逐处判断 |
| 返回 `null` | `getCar` / `getCategory` | 语义正确，但与上面两种混用后边界模糊 |

真正的缺陷是第一条。`guardSave` 原来是这样：

```ts
} catch {
  wx.showToast({ title: '保存失败，请检查输入后重试', icon: 'none' });
}
```

而实际抛出的错误是「记录不存在」—— 记录在别处被删了，**让用户去「检查输入」纯属误导**，他无论怎么改输入都保存不了。

### 46.2 定下分层约定（`services/service-error.ts`）

| 类别 | 规则 |
| --- | --- |
| **查询类**（getXxx / listXxx） | 查不到返回 `null` / 空数组。这是正常结果，不是错误 |
| **写入类**（saveXxx / updateXxx / removeXxx） | 前置条件不满足 → 抛 `ServiceError`，message **直接面向用户**，能原样进 toast |
| **可部分成功的操作**（导入 / 清空 / 批量恢复） | 返回 `{ ok, message?, ... }`，因为「部分成功」无法用异常表达，且调用方需要进度数字 |

为什么不用 `throw new Error` 直接抛：**无法区分这条错误该不该给用户看**。
`guardSave` 需要知道是显示具体原因、还是显示通用兜底。用独立类做标记，
运行时 `instanceof` 判断，不依赖 message 文本匹配。

```ts
export class ServiceError extends Error {
  constructor(message: string) {
    super(message);
    Object.setPrototypeOf(this, ServiceError.prototype);  // ES5 下 instanceof 会失效
    this.name = 'ServiceError';
  }
}
```

### 46.3 五处 throw 的文案重写

原文案面向开发者，改后面向用户：

| 位置 | 改前 | 改后 |
| --- | --- | --- |
| `updateCost` | `记录不存在` | `这条记录已被删除` |
| `updateRepair` | `记录不存在` | `这条记录已被删除` |
| `updateRefuel` | `记录不存在` | `这条记录已被删除` |
| `updateMaintainHandle` | `记录不存在` | `这条保养记录已被删除` |
| `saveRefuel` | `预设支出类别缺失` | `缺少「加油」类别，请到类别管理恢复` |

最后一条特别重要：不只说「缺什么」，还**告诉用户该做什么**。

### 46.4 `guardSave`：区分「业务错误」与「意外崩溃」

```ts
} catch (e) {
  lastRunAt.delete(key);           // 释放节流，允许立即重试
  wx.showToast({
    title: userMessageOf(e, opts.fallbackMessage ?? '保存失败，请重试'),
    icon: 'none'
  });
  return false;
}
```

- `ServiceError` → 显示自身 message
- 其它异常（`TypeError`、存储层原始错误）→ 显示通用兜底，**绝不把技术细节抛给用户**

### 46.5 顺带修掉一个真实缺陷：节流状态全局共享

`lastRunAt` 原来是**模块级单值**，所有页面共用一个 600ms 窗口：

> 在「记支出」页保存后，600ms 内切到「加油」页点保存 → **被静默忽略**，
> 用户点了保存但什么都没发生，也没有任何提示。

改为按**页面路由**分组（`getCurrentPages()` 栈顶的 `route`）：

- 同一页面内连点仍然节流
- 跨页面互不干扰
- 拿不到页面栈时退回固定 key，等同于旧行为，不会更糟

**为什么不用调用栈行号做 key**：我第一版就是这么做的，结果同一函数里换一行调用
就不共享节流窗口了 —— 太脆弱。页面路由是稳定标识。

## 47. 补齐错误契约文档：把「凭手感」变成「有依据」（2026-11-17）

### 47.1 上一轮只做了一半

第 46 节统一了错误处理机制（`ServiceError` + `guardSave` 传递原因），
但**只给 3 个函数补了注释**。剩下的函数里存在大量看似矛盾的行为：

| 函数 | 目标不存在时 | 看起来 |
| --- | --- | --- |
| `updateCost` | **抛错** | 不一致？ |
| `setCarIcon` | **静默返回** | 不一致？ |
| `removeCost` | **静默返回** | 不一致？ |
| `moveCategory` | **返回 false** | 不一致？ |

这些差异**其实都是合理的**，但依据只存在于开发者脑中 —— 这正是注释该补的地方。

### 47.2 提炼出的判据

> **用户是否「刚刚提交了一个明确的操作、且必须知道结果」。**

是 → 抛 `ServiceError`；否 → 静默返回 / 返回 `false`。

| 函数 | 行为 | 依据 |
| --- | --- | --- |
| `updateCost` / `updateRepair` / `updateRefuel` / `updateMaintainHandle` | 抛错 | 用户点了「保存」，正在等结果。记录在别处被删了必须告诉他，否则他以为存上了 |
| `setCarIcon` / `setCategoryIcon` / `setCategoryVisible` / `updateCategory` | 静默 | 用户正在选择器里操作，目标突然消失属罕见竞态。此时弹「记录不存在」既突兀又无动作可做 |
| `removeCost` / `removeRepair` / `removeRefuel` / `removeMaintain` / `removeMaintainHandle` | 静默 | 删除**幂等**：「已经没了」与「刚被我删掉」对用户是同一个结果 |
| `moveCategory` / `moveCategoryBy` | 返回 `false` | 「已经在最前/最后，移不动」是正常边界；调用方（拖动排序）需要区分「移动了」与「没移动」来决定是否重绘 |

一句话：**`updateXxx` 抛错是因为它承诺了「改完你能看到变化」，
而 `setXxxIcon` 只是附带动作、`removeXxx` 目标已达成、`moveCategory` 需要布尔结果。**

### 48.1 「推荐给朋友」只有文字能点：真机 bug 的根因

真机上点空白处和箭头都无反应，只有文字能点。根因是**两层**：

| 原因 | 说明 |
| --- | --- |
| **`opacity: 0.01`** | 我上一版为绕开「`opacity: 0` 不接收点击」改成 0.01。但**接近 0 的透明度在部分渲染层里仍会被判为不可交互**，直接跳过命中测试 —— 没解决根因，只是赌了一把 |

```css
  font-size: 0;                            /* 空按钮不被内置行高撑开 */
  line-height: 0;
  overflow: hidden;
```

### 48.3 底栏齿轮图标：为什么选 6 齿

图标是**手绘 SVG 的 base64 data URI**（小程序 WXML 不支持内联 `<svg>`），
统一规范：`viewBox 24×24`、`stroke-width 1.7`、`stroke-linecap/linejoin: round`、
描边态 `#6B7486`、选中态实心 `#3B6FF6`。齿轮严格沿用这套参数。

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 齿数 | **6** | 8 齿缩到 22px 时齿缝会糊在一起；6 齿每个齿更宽，齿形仍清晰 |
| 齿顶 / 齿根半径 | 9.3 / 6.7 | 齿高 2.6，是 22px 下仍能分辨的最小值 |
| 中心孔 | 3.4 | 太小（2.4）在描边态下会被描边吃掉，看起来像实心 |
| 齿顶半角 / 齿根半角 | 13° / 12° | 比 8 齿宽，齿更「厚实圆润」 |
| 齿顶形状 | **圆弧** | 直线会让齿轮显得「凶」，圆弧才符合现有图标的圆润感 |

路径用极坐标程序生成（`齿根 → 齿顶 → 齿顶圆弧 → 齿根 → 齿根圆弧` 循环），
不是手写坐标 —— 手写极易出现比例失真。选中态用 `fill-rule="evenodd"`
把中心孔挖空，避免「实心蓝圆盘」而不是齿轮。

图标 key 从 `user` 改为 `gear`（语义准确，且不再代表「用户」）。

### 48.4 底栏毛玻璃：0.62 → 0.38

**关键认知：毛玻璃看不明显，不是 blur 强度不够。**

底栏下方通常是页面底色 `#F5F6F8` 或卡片 `#FFFFFF`，**两者都接近纯白**。
毛玻璃的本质是「模糊底下**有对比度**的内容」——模糊一片接近纯白的纯色，
结果还是那片纯色，blur 再强也看不出来。

所以要让它明显，**唯一有效手段是降低不透明度**，让底下有颜色的东西透上来。
经四档对比（0.62 / 0.48 / 0.38 / 0.28）选定 **0.38**：
玻璃层次明显，图标仍清晰；0.28 在彩色内容（概览环图、统计彩色柱）上会糊。

配套加了**白色阴影兜底**：

```css
.tab-text { text-shadow: 0 1rpx 4rpx rgba(255, 255, 255, 0.9); }
.tab-icon { filter: drop-shadow(0 1rpx 3rpx rgba(255, 255, 255, 0.9)); }
```

文字用 `text-shadow`、图标（位图）用 `drop-shadow`（能贴合轮廓）。
这样压在任何底色上都能读，在浅色背景上又看不出痕迹。

## 50. 整体换肤：三套皮肤（2026-11-18）

### 50.1 约束与结论

用户明确要求：**只改皮肤，禁止改动任何布局、增删任何元素**。
因此三套皮肤只替换 CSS 变量，WXML 与 WXSS 的规则一行不改。

### 50.2 实现方式：`page-meta` 注入变量

```html
<page-meta page-style="{{pageStyle}}" />
```

`page-style` 把令牌写成内联样式落在 `page` 节点上，全页继承，**连 `page` 自身的背景色也能跟着变**。

深色皮肤下滚动到边缘会露出默认浅色底；`page-meta` 直接作用于 `page`，没有这个死角。

### 52.5 热修复：审计改动导致开发者工具报「Page route 错误(system error)」

审计后验证发现基础库 3.17.5 直接崩：

```
TypeError: Cannot read properties of null (reading 'screenHeight')
Page route 错误(system error): routeDone with a webviewId 5 is not found
TypeError: Cannot read properties of undefined (reading 'pages/reminder/index.html')
```

**根因**：审计新增的「onLoad 也注入皮肤」把 `applyNativeChrome`
（`wx.setNavigationBarColor` / `wx.setBackgroundColor`）也带进了 `onLoad`。
**onLoad 发生在路由完成之前**，此时调这两个原生外壳 API 会与路由动画竞争，
实测直接炸掉路由，三个报错连锁出现。

**修复**：
1. 职责拆开——`onLoad` 只调 `applyPageSkin`（纯 `setData`，路由前安全），
   原生外壳只在 `onShow` 调；
2. `applyPageSkin` / `applyNativeChrome` / `onShow` 注入段全部加 try/catch 兜底，
   皮肤是装饰性功能，任何异常都不能炸掉页面生命周期。

**教训**：包页面生命周期做横切关注点（皮肤注入）时，
**哪些 API 能在哪个生命周期阶段调用**必须逐个核实——`onLoad` 不是「onShow 的等价提前版」。

**验证**：typecheck 无错误、**57 套件 / 879 用例全绿**（新增 2 条源码断言锁定此约束）。

### 55.8 构建链修正：分包运行时必须是纯 JS（真机报 Invalid token 的根因）

**现象**：AI 编译模式里提问，`loadScriptSync` 报
`Failed to execute 'appendChild' on 'Node': Invalid or unexpected token`，
连锁导致 `module 'app.js' is not defined`、`Component is not found in path "wx://not-found"`。

**根因**：SKILL 的运行时代码最初写成 **TypeScript**。主包的 `.ts` 能被编译是因为
每个文件都在 pages 的引用链上；但 `skills/` 独立分包 `pages: []`、**没有任何页面引用它**，
开发者工具的 TS 插件不会编译这些文件 —— AI 编译模式把 `.ts` 原文当 JS 加载，
碰到 `interface` / 类型标注必然语法错误。

**修复**：把构建链固化为两段——

```
主包源码 ──sync──▶ skills-src/icar/lib（TS 镜像）
skills-src/**/*.ts ──tsc──▶ skills/icar/**/*.js（真机加载的唯一内容）
SKILL.md / mcp.json 直接放在 skills/icar/（静态文件不参与编译）
```

- 新增 `skills-src/tsconfig.json`（`rootDir: ./`、`outDir: ../skills`，产物保持目录结构）；
- `npm run build:skill` = tsc 编译 + **产物冒烟**（`scripts/smoke-skill-dist.js` 直接 require
  编译后的 JS，打桩 wx 走一遍三接口——产物层面的问题在本地就能暴露）；
- `project.config.json` 的 `packOptions.ignore` 增加 `skills-src` / `scripts`，
  TS 源码不进上传包；
- 测试新增守护：`skills/` 下**不得存在任何 `.ts`**（防止 TS 回流），运行时 JS 必须含
  `"use strict"` 且不含 `import` / `interface`。

### 55.9 口径修正：能耗的分母不是「有效里程」

真机跑通后核对 AI 回复，发现两处表述会让人对不上账：

**① 电耗的分母用错了**

`avgConsumption = 充电量 ÷ evMileage`，而文案配的是 `mileage.increased`（按记录首尾里程差算）。
两者在区间有缺口时不等，用户按「电耗 × 有效里程」反推总电量会对不上。
→ 新增 `consumptionMileage`（区间里程），文案改成
「平均电耗 14.29 kWh/100km（按 4,980 km 充电区间计），总有效里程 5,460 km」。

**② 「不含能耗」是凭空的差值**

原来只说「不含能耗费用 ¥1.934」，读者算不出能耗花了多少（差额 ¥747.36 消失了）。
→ 新增 `energyCost` / `energyCostLabel`，文案补「支出 ¥11,307.00，其中电费 ¥747.36」；
能耗为 0 时不写「其中油费 ¥0.00」这种废话。

同时 `SKILL.md` 加了一条硬规则：**能耗的分母是 `consumptionMileage` 而不是 `mileageIncreased`**，
避免模型自行改写时又把两个数配错。

**验证**：typecheck 无错误、**57 套件 / 957 用例全绿**（新增 3 条：能耗字段与空区间文案、
有能耗时「其中油费 / 按 500 km 区间计」两处措辞、产物冒烟）。

### 55.10 第二批接口：addRefuel + queryCars

首版只有 3 个接口，「记加油」这个最高频场景反而只能引导用户去页面，评测的「场景覆盖」分会吃亏。
补两个接口后共 5 个：`queryCars` / `queryStats` / `queryMaintain` / `addCost` / `addRefuel`。

**addRefuel 必须与主包 `saveRefuel` 同一套落库语义**，少一步就会长期错账：

```
insert fuelRecords → insert costs（关联 fuelRecordSourceId）→ 回写 costSourceId
→ 全量重算 fuelConsumptions（删旧插新）→ 回写车辆里程
```

最容易漏的是**关联支出**：只写加油记录不写 Cost，「今年花了多少」就会少这笔钱。
测试里专门断言了「加油后统计总额增加」。

**参数设计**：对话里用户常说「加满 40 升，320 块」，不会同时给单价。
因此 `volume` 必填，`unitPrice` 与 `amount` **二选一**，缺的那个反算（40L / ¥320 → ¥8.00/L），绝不写 0。

**其它行为**
- `isFull` 默认 true，但用户说「没加满」时必须传 false——两次加满之间的里程才算有效区间；
- `mileage` 不传则沿用车辆当前里程，并在文案里提示「如果这次里程不同请改一下」，不让用户误以为准确；
- 保存后立即反馈**本次算出的油耗**（`本次算出油耗 10.00 L/100km（区间 400 km）`），
  这是用户最想要的即时正反馈；算不出时说明原因（没加满 / 只有一条记录）。

**踩到的坑**：加油要靠系统预设类别 `presetType='refuel'` 归类。
预设被删过时 `addRefuel` 直接失败（这是对的，静默记到别的类别会造成错账），
但文案必须给出恢复路径（设置 → 支出类别管理）。冒烟脚本第一次就栽在这里。

**queryCars**：返回车名、能量类型、当前里程、是否置顶；置顶车排最前。
多车用户要记账或查统计前，模型可先调它确认 `carName`，减少「没找到车辆」的来回。

**测试（新增 9 条）**
- addRefuel：量 + 金额反算单价并同步写支出（统计 300 → 820、energyCost 320）；两次加满产出 10.00 L/100km；
  没加满不产出区间；缺量/缺钱先追问且不写库；缺里程沿用车辆里程并提示；
  加满后回写车辆里程（保养剩余量随之变化）；纯电车走充电口径（kWh）。
- queryCars：列出车辆与置顶标记；无车时给引导。

冒烟脚本同步扩到 5 个接口，并新增「加油后支出总额必须增加」的产物级断言。

**验证**：typecheck 无错误、**57 套件 / 957 用例全绿**、`npm run build:skill` 冒烟通过。

### 55.12 作用域与选车规则修正（多车用户的三个坑）

实测发现三个问题，根因是同一个：**把「没说哪辆车」当成了「就用第一辆」**。

**① 读操作只答一辆车**

「今年养车花了多少」问的是家底，返回「我的 CRV ¥11,307」是答非所问。
→ `queryStats` / `queryMaintain` 增加**全车作用域**：没说车名且有多辆车时，
返回合计 + 每车明细（统计按支出降序最多列 5 辆，保养最多列 5 项）。
单车用户行为不变。

**② 写操作静默挑车（最危险）**

多车用户说「停车 15」，接口按置顶车记下——钱记到了别人名下，**且不会报错**，
用户月底对账才发现。→ 新增 `resolveCarStrict`：单辆车直接用；说了车名模糊匹配；
**多辆车且没说 → 返回 `ambiguous`，由接口提示模型追问**，不写库。

**③ 说了车名但库里没有，仍按另一辆车回答**

原 `pickCar` 在匹配失败时回落到置顶车。用户问「老婆的车」而库里只有「我的 CRV」，
会拿到 CRV 的数字——比报错更糟。→ 读操作也改为严格匹配，匹配不上就报错并列出全部车名。

**关于蓝链点不开**

先做了一处确定性修正：`pagePath` 去掉前导斜杠，改为与 `app.json` 的 `pages` 数组**完全一致**
（`pages/statistics/index?id=...`）。平台按 app.json 匹配页面，多一个斜杠可能匹配不上。
新增测试遍历所有 `pagePath`：不得以 `/` 开头，且必须能在 `app.json` 的 `pages` 里找到。

> 仍未排除平台侧原因（如开发版对话界面不渲染 page-link、需要灰度用户的小微）。
> 若去掉斜杠后仍点不开，需要区分「文字没变蓝」与「蓝字点了没反应」两种症状，解法不同。

**测试（新增 7 条）**
- 多车：`queryStats` 不传车名返回合计 + 明细（¥500 / 2 辆）；传车名只统计那一辆；
  `queryMaintain` 不传车名汇总全部车；
- 写操作：多车且没说车 → `addCost` / `addRefuel` 都报错追问且**不写库**；带车名后写入正确的车（断言 `carSourceId`）；
- 路径：所有 `pagePath` 不带前导斜杠且存在于 `app.json`。

**验证**：typecheck 无错误、**57 套件 / 957 用例全绿**、`npm run build:skill` 冒烟通过。

## 56. 评测环境空数据：开发 / 体验环境自动预置演示数据（2026-11-20）

### 56.1 问题

评测工具拉起的模拟器是**空库**（无车辆、无记录），而 5 个原子接口全部依赖本地数据——
评测集 54 条正例大半答不出有效内容，服务交付 / 场景覆盖会塌。

确认过评测拉的是**体验版**（`envVersion === 'trial'`），这给了一个干净的解法：
**开发 / 体验环境的空库自动注入演示数据，正式版永不注入**。

### 56.2 实现（`services/demo-seed.service.ts`）

三道闸（`seedDemoDataIfNeeded(storage, envVersion)`）：

1. `release` 环境永不注入——正式版用户的数据承诺不破；
2. 已有车辆不注入——不覆盖真机上的真实数据；
3. `meta.demoSeededAt` 已存在不注入——用户删光演示数据 = 想要空库，必须尊重。

注入走**真实服务链路**而非裸写库：车辆走 `createCar`、加油/充电走 `saveRefuel`
（自动联动支出 + 全量重算油耗区间 + 回写里程）、保养走 `addMaintain` / `saveMaintainHandle`
（自动写 maintainLogs 关联流水 + 联动支出）、支出走 `saveCost`。
派生数据（油耗区间、保养剩余量）与 App 完全同源，不会出现「AI 一个数、App 一个数」。

数据规格对齐评测集需求（也是分镜表的「开拍前置」清单）：
3 辆车（燃油 + 纯电 + 混动，混动车显式传 `energyType` 加油/充电并存）、
燃油车两段有效油耗区间、纯电车电耗区间、保养一红（机油超期 300km）一橙（空气滤芯剩 450km）、
10 笔支出覆盖 4 个预设类别、跨 3 个月段（`atMonth` 计算带月末收敛与「当月不越过今天」钳制，
无论评测哪天跑，「这个月 / 上个月」都有数据）。

`app.ts` 的调用包 try/catch——注入失败只影响演示观感，绝不拖垮启动。

### 56.3 踩到的两个测试环境问题

1. **`getStorage()` 是模块级单例**：`resetStorage()` 清空 wx 桩后，单例不会重跑迁移与类别种子，
   `schemaVersion` 与预设类别全部丢失。生产不存在此问题（初始化只发生一次且先于注入）。
   → 测试的 `freshStorage()` 手动重建初始化状态（`seedPresetCategories` + 写回 `LATEST_SCHEMA_VERSION`）。
2. **`findLastHandle` 依赖 maintainLogs 关联流水**（`maintainSourceId → handleSourceId`），

   （实测空气滤芯算出 -2600 而不是 450）。
   → 测试里必须传 `storage.list('maintainLogs')`。这个坑对 SKILL 侧同样成立
   （`skills/icar` 的 `queryMaintain` 已正确传 logs）。

### 56.4 测试（新增 12 条，`tests/demo-seed.test.ts`）

- 三道闸：release 不注入 / 有车辆不注入 / develop 与 envVersion 缺失时注入；
- 数据规格：3 辆车能量类型、燃油两段油耗区间、纯电+混动充电记录、保养一红一橙
  （用 `calcRemaining` 实算断言）、支出 ≥8 笔 4 类别跨月、加油联动支出 ≥9 笔、meta 双字段；
- 幂等：清掉 `demoSeededAt` 后仍被「有车辆」闸挡住，计数不变。

另修复：种子里的类别缺失错误改用 `serviceError`（分层约定：服务层禁止裸 `throw new Error`）。

## 57. 首轮评测 21 分复盘：页面有效性靠 handoff，不是 page-link（2026-11-20）

### 57.1 评分结构

首轮评测：**综合 10 分 / SKILL 53 分**，其中

| 维度 | 分数 | 判定 |
| --- | --- | --- |
| 服务交付 | **21** | 严重不足 |
| ├ 文字有效性 | 100 | 表现较优 |
| └ 页面有效性 | **21** | 文字和页面关联性差 |
| 交互体验 | 99 | 表现较优 |
| 性能质量 | 100 | 表现较优 |
| 场景覆盖 | 100 | 表现较优 |

报告共列 **93 次页面有效性失败**，其中 92 次的原因完全一致：

> 本轮调用了开发者原子接口但**未触发页面接力（handoff）**，页面有效性检查未通过

### 57.2 根因

我把「回复里给一个蓝链」当成了页面跳转能力的全部。实际上官方有**三套互不替代**的机制：

| 能力 | 声明位置 | 用途 | 评测是否认可 |
| --- | --- | --- | --- |
| 文本混排链接 | `outputSchema` 的 `format: page-link` | 正文里插一条详情入口 | 仅影响文字 |
| **页面接力** | `mcp.json` 的 `_meta.ui.pagePath` + 接口返回 `handoff` | 把整段对话流程接力进页面 | **页面有效性认这个** |
| 账号卡片 | `agent.pageMetadata` | 没有合适接口时引导进页面 | 单独计分 |

我们只做了第一列，所以页面有效性几乎全灭。

### 57.3 修复

**① 5 个接口全部补上页面接力**

- `mcp.json` 每个接口加 `_meta.ui.pagePath`（统计页 / 车辆详情页，均为非 tabBar 页）；
- 接口返回 `handoff: () => ({ query, payload })`，`query` 里车 id 做 `encodeURIComponent`
  （官方明确：**平台不 decode，页面要自己 `decodeURIComponent`**）；
- `App.onLaunch` 注册 `wx.onAgentHandoff`，按 `pageId` 投递到 `globalData.agentHandoffs`；
- 新增 `utils/agent-handoff.ts` 的 `takeAgentHandoff(page)`：页面 `onLoad` 取走即删
  （避免 globalData 随对话轮次无限增长），拿不到或抛错一律返回 null，绝不影响页面打开；
- `pages/statistics` 与 `pages/vehicle-detail` 的 `onLoad` 消费 handoff，并对 `options.id` 做 decode。

**② 分类明细缺失（文字有效性问题）**

评测轨迹里「洗车总共花了多少」「这一年跑高速总共花了多少」被答成
「没有按类别统计的接口」——但主包 `stats.categories` 本来就算好了金额与占比。
→ `queryStats` 增加 `categories` 输出（前 3 类）并写进文案「分类上 加油 ¥1,256.00、停车 ¥120.00」。

**③ 车名匹配不上导致死循环**

「我两辆车分别什么时候该保养」被判 `blocked`（连续多次操作失败）：模型把「两辆车」
当车名传进来，接口报错、模型重试、再报错，最终卡死。
→ 多辆车时车名匹配不上**回落为全车汇总**，并在文案里说明「没有找到叫「X」的车，下面是全部 N 辆车的汇总」；
只有一辆车时仍然报错（不能假装就是那辆车）。

**④ 里程为 0 时不再输出「每公里 ¥0.000」**

那是误导，不是省钱。改为「区间内没有里程记录，暂时算不出每公里成本」。

### 57.4 测试（新增 7 条）

- `mcp.json` 每个接口都有 `_meta.ui.pagePath` 且路径不带前导斜杠；
- 5 个接口的返回值都带 `handoff`，且能生成含 `id=` 的 query；
- handoff 的 query 对车 id 做了编码（`mp%3Acars%3A`）；
- `queryStats` 返回 `categories` 且文案含分类金额；
- 多车 + 车名匹配不上 → 回落全车汇总并说明；单车 + 匹配不上 → 仍报错；
- 里程为 0 时不出现「每公里 ¥0.000」。

**验证**：typecheck 无错误、**58 套件 / 982 用例全绿**、产物冒烟通过。

### 57.5 评测暴露的种子数据问题（同批修复）

首轮评测的轨迹里能看到三处「数据不像真车主」的痕迹，全部已改：

### 57.6 接力落点修正：聚合问题不能落到单车页面

真机验证发现 handoff 触发了，但**落点错位**：

| 问题 | 原落点 | 问题 |
| --- | --- | --- |
| 「我有几辆车」 | 某辆车的详情页 | 问的是列表，却被带进一辆车 = 暗示系统默认了这辆车 |
| 「今年养车花了多少」 | 支出最高那辆车的统计页 | 文案讲的是全车合计，页面却是单车，**图文不一致** |

**修正原则：页面粒度必须与数据粒度一致。**

| 接口 | 数据粒度 | 接力页 |
| --- | --- | --- |
| `queryCars` | 全部车辆 | `pages/index/index`（我的车辆列表） |
| `queryStats` 全车汇总 | 全部车辆 | `pages/reminder/index`（概览） |
| `queryStats` 单车 | 单辆车 | `pages/statistics/index?id=…` |
| `queryMaintain` 全车 | 全部车辆 | `pages/reminder/index`（概览的保养提醒） |

这正是「掏出某辆车的数据」的来源。

**验证**：typecheck 无错误、**58 套件 / 982 用例全绿**（新增 2 条：读类接口接力页必须是聚合视图、
聚合接口 handoff 不带业务 query）。

## 51. 统计页环形图与图例双向联动（2026-11-18）

### 51.1 现象

概览页的分类环图支持「点扇区 ↔ 点图例」双向联动；统计页同样的环图**只能点扇区放大，图例完全没反应**。

### 51.2 根因：环图在组件里，图例在页面里

两页的实现方式不同：

| | 概览页 | 统计页 |
| --- | --- | --- |
| 环图 | 页面内直接画 `<canvas>` | 用 `donut-chart` 组件 |
| 选中状态 | 页面 `data.donutActive` | 组件内部 `data.activeIndex`（不对外） |
| 图例 | 页面渲染，`bindtap` 改 `donutActive` | 页面渲染，**无绑定** |

`donut-chart` 的选中状态是组件私有的，既没有对外暴露，也没有事件回传。
所以页面根本不知道用户点了哪个扇区，图例自然既点不动、也不会高亮。

### 51.3 修复：受控属性 + 事件

**组件**（`components/donut-chart/index.ts`）
- `activeIndex` 从内部 `data` 提升为 `properties`（受控）；
- 新增 `observers.activeIndex` 负责重绘；
- 点击扇区时 `setData` + `triggerEvent('change', { index })`，并把原来的显式 `draw()` 去掉（交给 observer，避免一次交互画两遍）。

**统计页**（`pages/statistics`）
- `data.catActive` 保存选中索引，传给组件并在 `bindchange` 里同步；
- 图例行加 `bindtap="onTapCatRow"` 与 `cat-on` 类，再点同一条取消选中；
- 数据重载（切维度 / 返回页面）时把 `catActive` 重置为 `-1`，避免索引越界。

### 51.4 布局零变化

图例要显示选中底色就需要内边距，但直接加 padding 会把内容挤窄。做法是用**负外边距抵消**：

```css
.cat-row {
  margin: 0 -12rpx;        /* 左右外扩，抵消 padding */
  padding: 8rpx 12rpx;     /* 上下合计 16rpx，正好接替原来的 margin-bottom 行距 */
  border-radius: 12rpx;
}
.cat-row.cat-on { background: var(--color-fill); }
```

内容起始位置与改动前一致，只是多了一圈点击热区；`.cat-list` 的 `margin-top` 由 8rpx 改为 0，避免与首行 padding 叠加。

### 51.5 测试（新增 9 条，`tests/donut-linkage.test.ts`）

- 组件把 `activeIndex` 提升为属性，且 `data` 里不再有同名副本；
- 有 `change` 事件回传、有 `activeIndex` observer、`onTap` 内不再重复 `draw()`；
- 统计页 wxml 绑定 `activeIndex` + `bindchange`，图例行有 `cat-on` 与 `bindtap`；
- 选中态用 `--color-fill`（与概览页 `.lg-on` 同语义）；
- 再点同一条取消选中、点图例做越界保护、数据重载清空选中。

**验证**：typecheck 无错误、**57 套件 / 879 用例全绿**。

**③ 深色皮肤进新页会先闪一帧浅色**
`pageStyle` 只在 `onShow` 注入，首次渲染拿不到 → 冷启动 / `navigateTo` 会先白一下。
→ `installSkinPatch` 同时包裹 `onLoad`（早于首帧）。

**④ `installSkinPatch` 的 `patched` 标记位置错误**
原实现先置 `patched = true` 再判断 `typeof Page === 'function'`，
在无 `Page` 的环境（如单测）会把标记永久置位，真机上再也没机会补装。
→ 移到成功替换之后。

**⑤ 导入旧备份会丢皮肤**
`io.service` 在「本地无 user」的分支里直接展开 `importedUser`，
旧备份没有 `skin` 字段 → 导入后回落到默认皮肤。
→ 补一个合法值兜底（`b` / `c` 才认，其余按 `a`）。

**⑥ 深色卡次级文字两套写法并存**
`pages/index/index.wxss` 的 `hero-sub` / `hero-unpin` / `hm-lbl` 仍用写死的
`rgba(255,255,255,.62/.72/.60)`，而 `vehicle-detail` 已改用 `--color-on-dark-sub`。
→ 统一走令牌（视觉几乎一致：`#A9ACB2` ≈ 白 62% 叠在深色卡上）。

**⑦ `setSkin` 注释与实现不符**
注释写「缺失时补建」，代码是 `if (!user) return`。
→ 改注释：不补建（补建要填十余个字段，写错反而污染数据）。

**⑧ 图表主题漏同步 `shadow`**
`applyChartTheme` 只同步了 8 个字段，深色皮肤下气泡阴影仍是浅色淡阴影（看不见）。
→ 深色用 `rgba(0,0,0,.45)`，浅色保持原值。
