## 保养数据刻意覆盖三种状态

概览页的「保养提醒 · N 项待保养」只有当 **剩余里程 ≤ 500 km** 或 **剩余天数 ≤ 15 天**
时才有内容；全部在周期内的话那个区块始终为空。所以每辆车都安排了：

| 车辆 | 已超期 | 即将到期 | 合计待保养 |
| --- | --- | --- | --- |
| 纯油 CRV | 轮胎换位（−850 km）、雨刮片（−81 天） | 玻璃水（+13 天） | **3 项** |
| 纯电 Model Y | 雨刮片（−100 天） | 玻璃水（+1 天）、轮胎气压检查（+7 天） | **3 项** |
| 混动 汉DM-i | 轮胎换位（−400 km）、电池散热滤芯（−95 天） | 轮胎气压检查（+13 天） | **3 项** |

导入 `icar-test-all.json` 后，概览页应显示「保养提醒 · 9 项待保养」，列表预览 3 条
（按「超期优先 → 剩余量少优先」排序）。

其余保养项都落在正常区间，用于对比两种样式。

## 其他数据特征

- **每条加油/充电都是「加满 / 充满」**：区间算法依赖锚点，这样才能生成完整区间，图表有数据
- **时间跨度覆盖 2026 全年**（1 月 ~ 11 月），可验证月 / 年 / 全部三种维度
- **保养项带 emoji 图标**，与 `DEFAULT_TEMPLATES` 一致，不依赖首次打开时的图标回填
- **`cycleUnit` / `cycleValue` 与 app 的 `buildCycleFields` 同规则**：
  有月周期写 `month + 月数`，否则有里程周期写 `km + 里程`
- **包含自定义支出类别「改装」**，用于验证分类占比图的标签避让
- 纯电车的充电记录带 `chargeBeforePercent` / `chargeAfterPercent`
- `fuelConsumptions` 留空，导入时由系统全量重算，顺带验证派生数据重建

## 保养状态的时效性

天周期项的「待保养」是**相对某个日期**算出来的，脚本以 **2026-11-17** 为基准日。
隔太久再导入，天周期项的状态会漂移（比如「玻璃水 +13 天」过两周就变成已超期）。
里程周期项不受影响。

如果发现待保养项数量和上表不一致，重新跑一次生成脚本即可。

## 重新生成

```bash
python test-data/generate.py
```

脚本用固定日期与固定数值，**每次生成结果一致**（只有导出时间戳 `exportedAt` 是固定的），
便于对比。生成时会在控制台打印每辆车的保养状态自检表，可以直接看到待保养项是否足够。

## 自动校验

`tests/test-data.test.ts` 会对四份文件做真实导入校验：

- 各类记录数量达标、能量类型正确
- 区间数量与能量类型分组正确（纯油 9 段、纯电 13 段）
- 油耗 / 电耗落在合理区间，不是 0 也不是荒谬值
- 纯电车 `fuelMileage` 为 0、`evMileage` 有值（审计修复的回归点）
- **保养项图标非空、`cycleUnit`/`cycleValue` 与周期一致**
- **待保养项数量与状态**（已超期 / 即将到期各几项，用固定基准日断言）
- **合并文件的三车聚合**：车辆数、建档后总里程、本年总支出、每车出行成本排序、9 项待保养
- 重复导入幂等（第二次全部 skipped，不产生重复记录）

```bash
npm test -- tests/test-data.test.ts
```

## 注意

- 导入是**合并**而非覆盖：`sourceId` 相同且 `updatedAt` 不更新的记录会被跳过。
  想从干净状态开始，先在开发者工具「清缓存 → 清除全部数据」再导入
- `icar-test-all.json` 与三个单车文件**使用相同的 `carSourceId`**，
  所以同时导入不会产生重复车辆（会被幂等跳过）；单独导入任一文件也能用
- 这是测试数据，**不要用于正式发布**，也不要混入真实数据后导出备份
